# Device test: checklist for Android and iOS

Deutsche Fassung: [geraetetest.md](geraetetest.md)

You work through this list on real devices with the example app from `example/`. It is necessary because the emulator and the simulator have no NFC: **Everything that involves NFC counts as verified only once this list has been completed.** For iOS, the results are below; for Android, the test on a real device is still pending. The SDK's simulator card bypasses reading the card and is not suitable for this.

## Prerequisites

- An Apple developer team with NFC entitlement (the capability "Near Field Communication Tag Reading" for the app identifier), and an NFC-capable iPhone with iOS 17.0 or newer.
- An Android device with extended-length NFC, Android 9 (API 28) or newer.
- An ID card or a test card with a known PIN, CAN and PUK. At the default Governikus test service, authentication succeeds only with a test card: a real ID card is read and the PIN is accepted, after which the flow ends with `AuthenticationCompleted (isSuccess: false, reason: Process_Certificates_From_Eac2_Cvc_Chain_Missing)` because the test service uses test certificates (observed this way on November 25, 2026). All rows up to the PIN entry can still be checked with a real ID card. For the test "PIN change with transport PIN", you need a card with a five-digit transport PIN.
- Network access to the Governikus test service.
- The example app runs on the device; see `example/README.md`.

**Caution:** The rows "Wrong PIN", "CAN case" and "PUK case" count down the card's failed attempts. After two wrong PINs, the card requires the CAN; after one more wrong PIN, it requires the PUK. Preferably use a test card for these. A correct PIN resets the counter to 3 (confirmed on an iPhone with a real ID card). However, a typo when entering the correct PIN costs another attempt.

## How to read the tables

At the very bottom of the "Protokoll" (log) section, the example app shows a list. Each line `Ereignis: <Name>` (event: name) is a plugin event, each line `Gesendet: <Befehl>` (sent: command) is a command that was sent, with the newest line on top. After the name of an event, its most important fields appear in parentheses, for example `PinRequested (Leser: …, Karte: ja, retryCounter: 3)` (reader: …, card: yes, retryCounter: 3). The log does not show addresses, because they can contain a session token; it shows only whether one is present (`URL: vorhanden`, URL: present). The column "Expected event" lists the names that should appear there. In the column "Result", enter whether it went that way (for example a check mark), and for deviations what appeared instead.

A failed `AuthenticationCompleted` or `ChangePinCompleted` additionally shows `failureKind: <kind>`: the kind that the plugin assigns to the `reason` (see "Failure kinds" in the README). The lines `NFC-Status: …` (NFC status) and `NFC-Einstellungen geöffnet: …` (NFC settings opened) come from the two buttons in the "NFC" section. The line `NFC: …` at the top of that section shows the last status: `verfügbar` (available), `ausgeschaltet` (switched off), `kein NFC` (no NFC) or `unbekannt` (unknown, after a failed query). It needs no running SDK, and the app updates it whenever it comes to the foreground.

Basic flow, which occurs in several rows. The tables call it "basic flow" for short; it consists of four steps and is not a single button:

1. Tap "SDK starten" (start the SDK).
2. In the section "Authentisierung" (authentication), leave the preset `tcTokenURL` and the switched-on "Entwicklermodus" (developer mode) and tap "Authentisierung starten" (start authentication). Expected: `AuthenticationStarted`, then `AccessRightsRequested`.
3. Tap "Akzeptieren" (accept). Expected: `InsertCardRequested`.
4. Hold the ID card against the device's NFC antenna.

You enter PIN, CAN and PUK in the "Eingabe" (input) field and send them with "als PIN senden" (send as PIN), "als CAN senden" (send as CAN), "als PUK senden" (send as PUK) or "als neue PIN senden" (send as new PIN). With real cards, do not leave the field empty.

## iOS

On iOS, the system shows its own NFC dialog while the card is being read. According to the SDK documentation, the SDK does not close this dialog when it asks for a PIN, CAN, PUK or new PIN; the app closes it with the command `INTERRUPT` (button "Unterbrechen", interrupt). On an iPhone 16 Pro with iOS 27.2.1, it is confirmed (November 25, 2026): the dialog stays open after `PinRequested`, and the app cannot be operated underneath it. An app must therefore close the dialog itself with `INTERRUPT` before it expects input.

In the "PIN, CAN, PUK" section of the example app, there is the switch "NFC-Dialog bei PIN-, CAN- und PUK-Abfrage automatisch schließen" (automatically close the NFC dialog when a PIN, CAN or PUK is requested). It is on by default: the app then sends `INTERRUPT` itself at `PinRequested`, `CanRequested`, `PukRequested` and `NewPinRequested`, and the log shows `Gesendet: INTERRUPT (automatisch)` (sent: INTERRUPT (automatic)). Leave the switch on unless a row says otherwise. If the NFC dialog appears again after sending the PIN, CAN or PUK, hold the ID card against the iPhone again.

`INTERRUPT` is allowed only directly after one of these four events. If you tap "Unterbrechen" at any other time, for example before placing the ID card, the SDK responds with `BadState`. This is the documented behavior of the SDK and not a defect of the plugin.
